# TrackItFoward Constitution

## Core Principles

### I. Laravel Conventions First

Code MUST follow the conventions of the installed framework major version (Laravel 13) before
any custom approach is considered.

- New classes MUST be generated with `./vendor/bin/sail artisan make:*` (including
  `make:class` for plain PHP classes) and passed `--no-interaction`.
- Validation MUST live in Form Request classes, not inline in controllers.
- Authorization MUST use Policies or Gates, not ad-hoc checks in controllers or views.
- Data access MUST use Eloquent models and relationships. Raw SQL is allowed only when Eloquent
  or the query builder cannot express the query, and the reason MUST be documented in a PHPDoc
  block.
- Internal links and redirects MUST use named routes via `route()`.
- APIs MUST use Eloquent API Resources and a versioned route prefix unless existing API routes
  in the application set a different convention.
- New code MUST match the structure, naming, and approach of sibling files in the same
  directory.

**Rationale**: Framework conventions are documented, familiar to every Laravel developer, and
supported by tooling. Deviating from them creates private knowledge that slows down reviews and
onboarding.

### II. Test-First Verification (NON-NEGOTIABLE)

Every behavior change MUST ship with automated PHPUnit tests that prove it works.

- Tests for new behavior MUST be written before or alongside the implementation, and MUST fail
  before the implementation makes them pass.
- Every bug fix MUST include a regression test that reproduces the bug.
- Tests MUST be created with `./vendor/bin/sail artisan make:test --phpunit {Name}` (add
  `--unit` for unit tests). Feature tests are the default; unit tests are for isolated logic
  with no framework or database dependency.
- Test data MUST come from model factories, using existing factory states where they exist.
  New models MUST ship with a factory.
- Tests MUST cover the happy path, validation failures, and authorization boundaries
  (guest, unauthorized user, authorized user) for every HTTP endpoint they touch.
- Database tests MUST run against the Sail PostgreSQL `testing` database configured in
  `phpunit.xml`, never against SQLite or the development database.
- External services (HTTP, mail, queues, storage, notifications) MUST be faked with Laravel's
  built-in fakes. Tests MUST NOT make real network calls.
- Throwaway verification scripts and tinker sessions MUST NOT be used in place of tests.
- A change MUST NOT be merged with failing, skipped, or deleted tests unless the skip or
  deletion is explicitly justified in the pull request.

**Rationale**: Tests are the only durable evidence that behavior is correct. Writing them first
keeps the design testable, and running them on the production database engine catches
dialect-specific bugs before deployment.

### III. Enforced Code Quality

Code quality rules MUST be machine-checkable wherever possible.

- All PHP MUST be formatted with Laravel Pint. `./vendor/bin/sail pint --dirty --format agent`
  MUST be run before every commit that touches PHP files.
- Every method MUST declare parameter types and a return type. Arrays passed across class
  boundaries MUST be documented with PHPDoc array shapes.
- Constructors MUST use property promotion. Empty zero-argument constructors MUST NOT exist
  unless the constructor is private.
- Control structures MUST use curly braces, including single-line bodies.
- Enum cases MUST use TitleCase.
- Names MUST describe intent (`isRegisteredForDiscounts`, not `discount`). Abbreviations are
  allowed only when they are standard domain terms.
- PHPDoc blocks are preferred over inline comments. Inline comments are allowed only to explain
  non-obvious logic, never to restate the code.
- Commented-out code, debug statements (`dd`, `dump`, `ray`, `var_dump`), and unused imports
  MUST NOT be committed.

**Rationale**: Automated formatting removes style debates from review. Explicit types catch
errors early and document intent. Consistent rules mean any file reads the same regardless of
who wrote it.

### IV. Maintainability & Simplicity

The simplest design that satisfies the current specification MUST be chosen.

- Features MUST NOT be built for speculative future requirements (YAGNI).
- Existing components, classes, and Blade views MUST be reused before new ones are written.
- New top-level directories under `app/` or the project root MUST NOT be created without
  explicit approval.
- New Composer or npm dependencies MUST NOT be added without explicit approval. A dependency
  MUST be justified by a capability the framework does not already provide.
- Controllers MUST stay thin. Business logic that is reused or longer than a few statements
  MUST move into a dedicated class (for example, an Action or Service) generated with
  `./vendor/bin/sail artisan make:class`.
- Classes and methods MUST each have a single, clearly stated responsibility.
- Every migration MUST define a working `down()` method so it can be rolled back.
- N+1 queries MUST be prevented with eager loading, and lists that can grow unbounded MUST be
  paginated.
- Any deviation from these rules MUST be recorded in the plan's Complexity Tracking table with
  the reason the simpler alternative was rejected.

**Rationale**: Every abstraction, directory, and dependency is a long-term maintenance cost.
Requiring justification keeps the codebase small enough to understand and change safely.

### V. Sail-Only Execution

All project commands MUST run inside the Laravel Sail containers by prefixing them with
`./vendor/bin/sail`. Host-installed PHP, Composer, Node, and database clients MUST NOT be used
for project commands.

| Task                  | Required command                                   |
| --------------------- | -------------------------------------------------- |
| Start / stop services | `./vendor/bin/sail up -d` / `./vendor/bin/sail stop` |
| Artisan               | `./vendor/bin/sail artisan {command}`              |
| Run tests             | `./vendor/bin/sail artisan test --compact`         |
| Format PHP            | `./vendor/bin/sail pint --dirty --format agent`    |
| Composer              | `./vendor/bin/sail composer {command}`             |
| npm / Vite            | `./vendor/bin/sail npm {command}`                  |
| Tinker                | `./vendor/bin/sail artisan tinker`                 |
| Database shell        | `./vendor/bin/sail psql`                           |

- Documentation, specs, plans, tasks, and scripts MUST write commands in this form.
- Where runtime agent guidance (for example `CLAUDE.md` or `AGENTS.md`) shows a bare
  `php artisan`, `composer`, `npm`, or `vendor/bin/*` command, it MUST be run with the
  `./vendor/bin/sail` prefix instead.

**Rationale**: The host and the container differ. The Sail runtime uses PHP 8.5 and
PostgreSQL 18, while the host PHP is a different version and has no access to the container
database. Running everything through Sail means every developer, agent, and CI run uses the same
environment.

## Technology Stack & Constraints

- **Runtime**: PHP 8.5 (Sail runtime); `composer.json` requires PHP ^8.3.
- **Framework**: Laravel 13.
- **Database**: PostgreSQL 18 via Sail. The `testing` database is used by the test suite.
- **Testing**: PHPUnit 12. Pest MUST NOT be introduced without amending this constitution.
- **Formatting**: Laravel Pint, using its default Laravel preset unless a `pint.json` is added
  by amendment.
- **Frontend**: Vite 8 with Tailwind CSS 4.
- **Developer tooling**: Laravel Boost (MCP server, agent guidelines, and skills). Before
  writing code that depends on ecosystem APIs, contributors and agents MUST check the installed
  package version (`./vendor/bin/sail composer show {vendor/package}`) and use the APIs for that
  version.
- **Secrets**: Credentials MUST come from environment variables via `config()`. `env()` MUST
  NOT be called outside `config/` files, and `.env` MUST NOT be committed.

## Development Workflow & Quality Gates

Every change MUST pass these gates, in order, before it is merged into `main`:

1. **Plan gate**: For Spec Kit features, the plan's Constitution Check MUST pass Principles
   I–V, or record each violation in Complexity Tracking.
2. **Test gate**: The narrowest relevant tests MUST pass during development
   (`./vendor/bin/sail artisan test --compact --filter={TestName}` or a file path). The full
   suite (`./vendor/bin/sail artisan test --compact`) MUST pass before merge.
3. **Format gate**: `./vendor/bin/sail pint --dirty --format agent` MUST leave no changes.
4. **Migration gate**: New migrations MUST run with `./vendor/bin/sail artisan migrate` and
   roll back with `./vendor/bin/sail artisan migrate:rollback` without errors.
5. **Review gate**: A reviewer MUST confirm the change follows this constitution, including
   test coverage for the behavior added or changed.

Commits MUST be small and focused on one concern, with messages that state what changed and why.

## Governance

This constitution supersedes all other project practices, guidelines, and agent instructions.
Where `CLAUDE.md`, `AGENTS.md`, skills, or templates conflict with it, this constitution
prevails, and the conflicting file SHOULD be updated to match.

- **Amendments**: Proposed in a pull request that edits this file, updates the Sync Impact
  Report, and explains the reason for the change. Amendments take effect when merged.
- **Versioning**: Semantic versioning applies to this document.
  - MAJOR: A principle is removed or redefined in a backward-incompatible way.
  - MINOR: A principle or section is added, or guidance is materially expanded.
  - PATCH: Clarifications, wording, or typo fixes that do not change meaning.
- **Compliance review**: Every `/speckit-plan` MUST evaluate the Constitution Check gate, and
  every code review MUST verify compliance. Unjustified complexity is grounds to reject a
  change.
- **Runtime guidance**: Day-to-day agent guidance lives in `CLAUDE.md` and `AGENTS.md`
  (generated by Laravel Boost) and the skills under `.claude/skills/`. These files supplement
  this constitution but do not override it.
